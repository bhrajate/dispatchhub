# 性能定位与目标

> 这份文档回答两个问题：
>
> 1. **任务中台这一类系统通常的性能要求是什么？**（行业量级感）
> 2. **DispatchHub 当前在哪一档，距离"可用"还差多少？**（自我定位）
>
> 不回答"具体优化怎么做"——那是 [reports/](./reports/) 与 [optimizations/](./optimizations/) 的事。这里是**目标讨论**，用来在每次性能讨论之前对齐"我们要做到什么"。

## 一、任务中台没有统一的性能基准

任务调度 / 异步任务平台这一类系统，量级跨度可以从**每天几千个 cron**到**每秒几万次提交**——全看承载哪类业务。先做业务定档，再谈 RPS。

### 按业务类型的量级感

| 业务类型 | Submit QPS | 在线任务数 | 时延要求 | 例子 |
|---|---|---|---|---|
| **内部运维 / DevOps** | 1-50 | 10-1000 | 分钟级 | CI/CD、备份、报表 |
| **后台异步业务**（中小厂主流） | 50-500 | 1万-10万 | 秒级 | 邮件 / 短信 / 推送、订单后处理、文件转码 |
| **互联网大厂常规业务** | 500-5000 | 10万-100万 | 亚秒 - 秒级 | 内容审核、营销触达、消息分发 |
| **超大规模 / 实时风控类** | 5000-50000+ | 百万 - 千万级 | < 100ms | 风控决策、推荐 trigger、广告竞价排队 |
| **数据 / AI 流水线** | 1-100（粗粒度） | 1万-10万 | 关心吞吐而非单次延迟 | Spark 调度、训练任务编排 |

> 大多数公开能查到的 Asynq / Sidekiq / Celery / Temporal 用户案例落在 **第 2-3 档**（每秒几百到几千 submit）。**第 4 档以上通常会自研或重度改造开源框架**——这一档的瓶颈往往不在 submit，而在 worker 调度延迟和持久化层。

### 横向参考点（截至 2026-05）

- **Asynq**（Go + Redis 单实例）：submit 5k+ RPS，社区报告。
- **Sidekiq**（Ruby + Redis）：submit 数千 RPS，Sidekiq Pro/Enterprise 可推到更高。
- **Temporal**（Go + Cassandra/PostgreSQL）：单 frontend 几 k start RPS，集群可线性扩。
- **Celery**（Python + RabbitMQ/Redis）：submit 通常被 Python overhead 限制在百-千量级。

这些数字**不能直接对比**——后端存储、是否持久化、是否做 dedup、单任务字节大小都不同。
仅作"量级感"参考。

## 二、Submit RPS 只是一个维度

**业务说"我要 500 RPS"，多半实际意思是"submit 不丢、调度延迟稳、worker 不积压"。
这三件事不是同一个数字。**

| 维度 | 含义 | 测起来难点 |
|---|---|---|
| **Submit RPS** | 客户端能多快塞进任务 | 容易，常被当作唯一指标 |
| **调度延迟** | 任务从入队到 worker 拿到的时间（p50 / p99） | 业务最关心的"任务多久跑起来"，常落在 10ms-1s |
| **执行吞吐** | 集群每秒完成多少任务 | 受 worker 数量、单任务耗时、资源限制 |
| **延迟任务精度** | `delay=30s` 的任务真的 30s ± 多少跑？ | 调度器扫描周期决定下限，常见 ±100ms 到 ±5s |
| **背压能力** | 提交速度 > 执行速度时如何（拒绝 / 排队 / 降级）？ | 大多数事故来源 |
| **重试 / 重复抑制** | 失败重试不雪崩、不重复执行 | exactly-once 是经典难题 |
| **可用性 SLO** | 99.9%? 99.99%? | 决定持久化与一致性策略 |
| **数据一致性** | 任务被写入到 worker 真的看到，丢了多少？ | 见 [analysis/task-submit-dual-write-consistency.md](../analysis/task-submit-dual-write-consistency.md) |

性能讨论时**只看 Submit RPS 是危险的**：可能跑出漂亮的 submit 数字，但调度延迟、背压、一致性出问题，业务体感反而比 submit 慢但稳定的系统更差。

## 三、DispatchHub 当前位置

### 已测维度（仅 dev 环境，i5-13500H WSL2）

参考 [reports/r1-i5-13500h-2026-05-19.md](./reports/r1-i5-13500h-2026-05-19.md)：

| 维度 | r1 (优化 A 后) | 备注 |
|---|---|---|
| Submit RPS（HTTP 写路径） | **100** PASS / 300 FAIL | 单 apiserver |
| Submit RPS（gRPC SubmitTask） | **100** PASS / 300 FAIL | 同 |
| GET task（MySQL 读） | 1000 未压顶 | 多核并行 |
| Queue stats（Redis 读） | 1000 未压顶 | CPU 余量大 |

### 未测维度（**全部空白**）

- 调度延迟（任务入队 → worker pickup 的 p50 / p99）
- 执行吞吐（集群每秒完成多少任务）
- 延迟任务精度（`delay=30s` 实际 ± 多少）
- 背压行为（饱和段除了 5xx 还能不能优雅降级）
- 重试压力（重试 storm 时 apiserver 表现）
- 多实例线性度（2 个 apiserver 副本能不能 200 RPS）
- 失败注入下的行为（MySQL/Redis/etcd 故障恢复）
- 持久负载（1 小时、24 小时不漂移）

### 在第一节分档表里的位置

```
内部运维 (1-50)  ─────[当前位置: 100 RPS]──── 后台异步 (50-500)  ──── 大厂业务 (500-5000) ──── 超大规模 (5k+)
                       └─单实例─┘
                                            └────集群 3-5 副本可能够到下限────┘
```

**功能上能用，处于"内部运维档与中小厂后台业务档之间"**。距离"通用任务平台合理 baseline"还有 1-2 个数量级。

## 四、合理目标（如果 DispatchHub 定位为通用任务平台）

下面是**讨论用基准**，不是承诺：

| 指标 | 单实例目标（dev 配置） | 集群目标 | 当前 |
|---|---|---|---|
| Submit RPS（写） | 1k-3k | 5k+（≥3 副本线性扩） | 100 ❌ |
| Submit RPS（读 GET task） | 5k-10k | 不构成瓶颈 | 1k+ 未压顶 ✓ |
| 调度延迟 p99（普通任务） | < 100ms | < 100ms | **未测** |
| 延迟任务精度 | ±100ms | ±100ms | **未测** |
| 持久负载 1 小时漂移 | 内存 / goroutine 不漂移 | 同 | **未测** |
| 失败注入下行为 | 优雅降级、不雪崩 | 单节点失败不影响整体 | **未测** |
| 横向扩容线性度 | — | 加副本 RPS 近线性 | **未测** |

为什么定 1k-3k：

- 与 Asynq 单实例（5k+）保持 1 个数量级以内
- 让一个 4 核小型实例足以喂饱单个业务线（业务峰值 < 1k RPS 是大多数中型业务的真实情况）
- 单核满载架构（当前模式）极限大约就在这个量级，再往上要么并发化 IO（B 优化），要么改连接池/分片

## 五、决定下一步要先回答两个问题

### Q1：DispatchHub 想承载的目标场景是什么？

| 选项 | 影响 |
|---|---|
| **自用 / 内部小工具** | 100 RPS 已经够，重点放在功能完整性、可观测性 |
| **开源通用任务平台** | 必须做到 1k+ / 单实例，否则用户会选 Asynq |
| **大厂内部业务平台** | 需要明确承载哪条业务线、估算峰值 QPS，按业务定指标 |
| **超大规模 / 风控类** | 当前架构（单 apiserver + Redis + MySQL）需要重新设计——大概率应该 fork 改造而不是用作通用平台 |

### Q2：业务实际峰值 QPS 估算？

- 如果 < 100：当前能用，不必继续单机优化，直接做集群与失败注入测试。
- 如果 100-1000：写路径还有 5-10 倍优化空间，应继续做 B（并发 IO）、C（异步日志）等。
- 如果 > 1000：单实例优化必须做完，且要规划 ≥ 3 副本横向扩容方案。
- 如果 > 5000：当前架构可能需要重新设计存储路径，不是单纯调优。

回答了这两题，才能判断"下一步是继续单机优化、还是开始集群验证、还是直接做架构演进"。
