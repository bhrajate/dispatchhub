> **轮次**：r1（第一轮优化）
> **CPU**：Intel Core i5-13500H (16 vCPU, WSL2)
> **采集日期**：2026-05-19
> **改动**：`gorm.Config{SkipDefaultTransaction: true}`（一行）
> **产物归档**：`test/perf/results/r1-i5-13500h-2026-05-19/`
> **基线**：[r0-i5-13500h-2026-05-19.md](./r0-i5-13500h-2026-05-19.md)
> **过程复盘**：[../optimizations/r1-postmortem-2026-05-19-write-path.md](../optimizations/r1-postmortem-2026-05-19-write-path.md)

## 背景

[r0 baseline](./r0-i5-13500h-2026-05-19.md) 显示写路径在 ~300 RPS 撞上 apiserver
单核 CPU 满载。CPU profile（`/debug/pprof/profile?seconds=30`，600 RPS @ 30s）
把 `SubmitTask` 14.93s 的耗时拆为：

| 路径 | cum | 占比 |
|---|---|---|
| `taskStore.Create` (MySQL) | 10.81s | 73% |
| ├─ gorm `BeginTransaction` | 4.33s | 29% |
| ├─ 实际 INSERT 执行 | ~5.0s | ~33% |
| └─ gorm `CommitOrRollback` | 1.48s | 10% |
| `broker.Enqueue` (Redis) | 2.49s | 17% |
| `afterSubmit` (zap log + metrics) | 1.37s | 9% |
| `routeValidator.Validate` | 0.07s | 0.5% |

GORM 默认给每条 `Create()` / `Update()` 包一层 `BEGIN` … `COMMIT`，多走 2 个 RTT。
本仓库 `internal/`、`pkg/`、`cmd/` 全量 grep 没有任何显式 `db.Transaction` / `Begin`，
所有写都是单语句操作。**`SkipDefaultTransaction: true` 全局开是安全的**。

## 改动

仅一处，`internal/shared/infrastructure/persistence/factory.go::NewMySQLDB`：

```go
db, err := gorm.Open(mysql.Open(cfg.DSN), &gorm.Config{
    SkipDefaultTransaction: true,
})
```

apiserver 与 scheduler / worker 共用同一个 `NewMySQLDB`，所有进程一并受益。

## 同矩阵对比（vs r0 baseline）

| 接口 | 阶梯 | 指标 | r0 baseline | r1 (优化 A) | 变化 |
|---|---|---|---|---|---|
| `POST /api/v1/tasks` | 100 | actual / p99 / CPU% | 100 / 246ms / 24% | 100 / **69ms** / **17%** | p99 −72%，CPU −29% |
| `POST /api/v1/tasks` | 300 | actual / p99 / errors / CPU% | 298 / 1660ms / 16% / 106% | 298 / 2230ms / 10% / 90% | errors −38%（仍 FAIL） |
| `POST /api/v1/tasks` | 600 | actual / p99 / CPU% | 314 / 28s / 108% | **434** / 17s / 123% | RPS **+38%** |
| `POST /api/v1/tasks` | 1000 | actual / p99 / CPU% | 267 / 44s / 102% | **380** / 37s / 106% | RPS **+42%** |
| gRPC `SubmitTask` | 100 | actual / p99 / CPU% | 100 / 181ms / 51% | 100 / **101ms** / 44% | p99 −44% |
| gRPC `SubmitTask` | 300 | actual / errors | 272 / 0.3% | 255 / 7% | 见说明 ⁽²⁾ |
| `GET /api/v1/tasks/{id}` | 1000 | actual / p99 / CPU% | 1000 / 477ms / 168% | 1000 / 315ms / 158% | 持平（读路径不受影响是预期） |

r1 的 7% 仍超 1% verdict 阈值。**关键看 r0/r1 都 FAIL，verdict 没翻 PASS**，并不是
A 把 PASS 改 FAIL。

## 结论

1. **饱和段写入吞吐 +38–42%**：600 / 1000 RPS 阶梯实际 RPS 显著抬高，与 profile
   中 BEGIN+COMMIT 占比 39% 的估计一致。
2. **轻负载尾延迟降七成**：100 RPS p99 从 246ms → 69ms（HTTP）、181ms → 101ms（gRPC）。
3. **最高通过阶梯仍是 100 RPS**：300 RPS errors 从 16% 降到 10%，但仍超过 1% 阈值
   → 下一瓶颈不在 BEGIN+COMMIT，而是别的。
4. **读路径不受影响**：符合预期（GORM 单语句 SELECT 本身不加事务包装）。

## 下一步候选

- **B：MySQL INSERT + Redis Enqueue 并发执行（`errgroup`）**：profile 中 Redis
  Enqueue 占 17%，与 MySQL 串行后总耗时 = MySQL + Redis；并发后 = max(MySQL, Redis)，
  单请求耗 CPU 时间预计再降 ~15%。需要梳理"Redis 失败靠 scheduler 30s 内补偿"的
  语义边界。
- **抓 300 RPS errors 的来源**：从 apiserver.log 或 wrk2 stdout 看错误是 5xx 还是
  连接被拒；如果是 RouteValidator fail-open + worker 真拒收，需要看 worker 侧；
  如果是 MySQL 连接池打满，需要调 `MaxOpenConns`（当前 50，1000 RPS × 单请求
  ~20ms = 20 in-flight，按理够，但 QPS bursty 时可能撞）。
- **重新跑 CPU profile**：在 A 上线后 600 RPS 跑一次，看新 top 是不是 Redis
  client 编码 / `net.(*conn).Write`，再决定 B 的优先级是否仍最高。
