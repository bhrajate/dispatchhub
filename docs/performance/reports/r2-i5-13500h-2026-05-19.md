# r2 — i5-13500H — 2026-05-19：优化 D（MySQL 连接池调优）

> **轮次**：r2（第二轮优化，叠加在 r1 之上）
> **CPU**：Intel Core i5-13500H (16 vCPU, WSL2)
> **采集日期**：2026-05-19
> **改动**：MySQL `max_idle_conns` 10 → 50（与 max_open_conns 同），新增 `conn_max_idle_time: 5m`
> **产物归档**：`test/perf/results/r2-i5-13500h-2026-05-19/`
> **基线**：[r1-i5-13500h-2026-05-19.md](./r1-i5-13500h-2026-05-19.md)

## 背景

[r1](./r1-i5-13500h-2026-05-19.md) 之后，写路径在 300 RPS 仍 FAIL（errors 10%、p99 2.2s），但 actual_rps 已经到 300，**问题不在 RPS 上限，而在错误率**。按 [roadmap §F2](../optimization-roadmap.md) 先做了根因定位：

直接在 300 RPS 压测时 tail apiserver.log，分类错误：

```
1964 / 1964 = 100% 是 "submit task: persist task: driver: bad connection"
  15      "submit task: persist task: context canceled"  (client timeout 残留)
```

结合 OS 层观察：

```
ss -tan | grep 33307
   50 ESTAB     ← max_open_conns 上限
   45 TIME-WAIT ← idle 连接被关后留下的 TCP 残骸
```

**根因**：`MaxIdleConns: 10` 远低于 `MaxOpenConns: 50`。压测峰值连接数会到 50；当 in-flight 短暂回落，超过 10 的 idle 连接会被 `database/sql` 主动关闭；下一次需求又重新 dial。这个 churn 过程中：

- 客户端有时拿到一个 server 端已先关掉的"幽灵"连接 → `driver: bad connection`
- TCP TIME-WAIT 堆积（loopback 上 `tcp_tw_reuse=2`，回环禁用 reuse，TIME-WAIT 至少 60s 不能复用同 (sport,dport) 元组）

## 改动

`internal/shared/infrastructure/config/config.go::MySQLConfig` 新增 `ConnMaxIdleTime`，`factory.go::NewMySQLDB` 调 `sqlDB.SetConnMaxIdleTime`。

`test/perf/configs/apiserver.yaml` 与 `config/apiserver.yaml`：

```diff
 mysql:
   max_open_conns: 50
-  max_idle_conns: 10
+  max_idle_conns: 50          # 与 max_open_conns 同，避免 idle conn churn
   conn_max_lifetime: 1h
+  conn_max_idle_time: 5m      # 短于 MySQL wait_timeout (28800s)，主动关 idle 防 stale
```

## 关键观察

1. **写路径最高通过阶梯：100 → 300 RPS**（HTTP 与 gRPC 都通过）。这是 r0 → r1 → r2 三轮里**第一次最高 PASS 阶梯翻番**。
2. **饱和段错误率几乎归零**：r1 的 600/1000 阶梯 errors 22-23%，r2 全降到 0-0.2%。
   bad connection 被根除后，饱和现象只剩"actual_rps 不达标"一种 —— 单核 CPU 仍是上限，不再叠加 connection churn 这一层抖动。
3. **CPU 占用反而下降**（300 RPS 90% → 60%）。原因：bad connection 触发 `database/sql` 内部 retry，每个失败请求会消耗 2-3 倍 CPU；root cause 修掉后这些被浪费的 CPU 释放出来。
4. **300 RPS p99 从 2230ms → 142ms**（−94%）：连接池 churn 是 r1 阶段尾延迟的真正主因之一，profile 看不到（只看 cpu time）但行为后果显著。

## 结论

1. **300 RPS 阶梯 verdict FAIL → PASS**（HTTP & gRPC）。**最高通过阶梯 100 → 300**，业务可承载并发提升 3x。
2. **r0 → r1 → r2 累计**：写路径 100 RPS p99 从 246ms → 69ms → 48ms（−80%）；
   300 RPS 从 errors 16% / FAIL 到 errors 0% / PASS。
3. **600 RPS 仍 FAIL** 但失败模式变了：r1 是"errors 22%"，r2 是"actual 429 达标率 71%"。下一刀的方向不再是"修连接池稳定性"，而是"提单核 CPU 处理速度"。
