## 1. 方法论

- **工作负载模型**: open-model 固定 RPS 阶梯注入，非 closed-model VUs
- **测量窗口**: 30s/cell
- **阶梯**: 100 / 300 / 600 / 1000 RPS
- **Verdict 规则**: `error_rate ≤ 1%` 且 `actual_rps ≥ target × 95%`
- **协议覆盖**: HTTP (wrk2) + gRPC (ghz)

### 并发与连接配置

| 协议 | 并发数 (Concurrency) | 连接数 (Connections) | 说明 |
|---|---|---|---|
| HTTP (wrk2) | `RPS / 50`，最小 50 | = 并发数 (wrk2 `-c` 参数) | wrk2 的 `-c` 同时控制并发和连接 |
| gRPC (ghz) | `RPS / 50`，最小 50 | 50 (`CONNECTIONS=50`) | ghz 通过 `--connections` 配置 |

**并发计算公式**: `concurrency = max(RPS / 50, 50)`

| 目标 RPS | 并发数 | HTTP 连接数 | gRPC 连接数 |
|---|---|---|---|
| 100 | 50 | 50 | 50 |
| 300 | 50 | 50 | 50 |
| 600 | 50 | 50 | 50 |
| 1,000 | 50 | 50 | 50 |

> **跨协议 p99 比较注意**: wrk2 的 HdrHistogram 修正了 coordinated omission，ghz **没有**。
> ghz 的 p99 通常显著低于 wrk2，差异来自测量工具而非服务性能。
> 跨协议只比较达标率与 verdict，p99 仅在同一协议内横向比较。

## 5. gRPC 连接数对比分析 (connections=1 vs connections=50)

本次为 r3 复测，使用 `CONNECTIONS=50`，与 r3 原始测试 `CONNECTIONS=1` 的结果对比如下：

### gRPC `SubmitTask` 对比

| 目标 RPS | connections=1 actual | connections=50 actual | 变化 | connections=1 p99 | connections=50 p99 | 变化 |
|---|---|---|---|---|---|---|
| 100 | 99.9 | 99.9 | 0% | 25.5 ms | 15.9 ms | -38% |
| 300 | 299.9 | 299.9 | 0% | 17.5 ms | 20.2 ms | +15% |
| 600 | 599.9 | 599.9 | 0% | 37.4 ms | **225.7 ms** | **+503%** |
| 1,000 | **927.3** | 772.7 | **-17%** | 222.8 ms | 270.7 ms | +22% |

### HTTP `POST /api/v1/tasks` 对比

| 目标 RPS | connections=1 actual | connections=50 actual | 变化 | connections=1 p99 | connections=50 p99 | 变化 |
|---|---|---|---|---|---|---|
| 100 | 100.3 | 100.6 | 0% | 300.8 ms | 263.4 ms | -12% |
| 300 | 300.2 | 300.2 | 0% | 543.2 ms | 24.7 ms | **-95%** |
| 600 | 599.9 | 599.9 | 0% | 587.3 ms | 61.2 ms | **-90%** |
| 1,000 | **996.0** | 907.7 | **-9%** | 473.1 ms | 3,592 ms | **+660%** |

### 关键发现

1. **gRPC 多连接反而更差**: `connections=50` 在 600 RPS 时 p99 暴涨 503% (37ms → 226ms)，1000 RPS 时 actual 下降 17% (927 → 773)。
   - **原因分析**: gRPC 单连接已支持 HTTP/2 多路复用，增加连接数带来的收益被连接管理开销抵消。50 个连接意味着 50 个独立的 TCP 连接和 HTTP/2 流，服务端需要处理更多连接状态，在写路径 I/O bound 场景下反而增加了竞争。
2. **HTTP 低 RPS 延迟改善但高 RPS 崩溃**: 300-600 RPS 时 p99 大幅改善 (-90%~-95%)，但 1000 RPS 时 p99 从 473ms 飙升到 3.6s，actual 从 996 降到 908。
3. **结论**: 对于当前写路径 (MySQL 持久化 + Redis LPUSH)，**gRPC 单连接是最优配置**。多连接在 I/O bound 场景下无收益，反而增加开销。

## 6. 已知限制与后续方向

1. **gRPC 单连接即最优**: 测试表明 `connections=1` 是当前最优配置，无需增加连接数
2. **写路径天花板 ~600-1000 RPS**: HTTP 在 1000 RPS FAIL (actual 908)，gRPC 在 1000 RPS FAIL (actual 773)。瓶颈在 MySQL + Redis 串行 I/O
3. **读路径可扩展到 1000+ RPS**: MySQL 读和 Redis 读在 1000 RPS 时 CPU 分别为 36% 和 19%，远未饱和
4. **测量窗口 30s**: 可能导致 p99 波动，建议后续恢复 60s
