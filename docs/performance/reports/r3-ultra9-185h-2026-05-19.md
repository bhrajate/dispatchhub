# DispatchHub Performance Report r3 — 2026-05-19 (Intel Ultra 9 185H)

> ## ⚠️ 勘误（2026-05-20 补）：gRPC 数字基于有偏的 driver 配置
>
> ### 已验证事实
>
> - `ghz` 文档明确 `--connections` 默认 `1`：*"Number of connections to use. Concurrency is distributed evenly among all the connections (default 1)"*。本报告 driver（修订前）未指定 `--connections`，因此**所有 `--concurrency` 个并发流共享一条 TCP / HTTP/2 连接**。
> - 单 HTTP/2 连接有单 read-loop、单 write-loop、单 outbound flow-control window，单连接 frame 处理速率成了 ghz 这一侧的天花板。
>
> ### 高置信度推论（**未在本机 `ss -tan` 实测**）
>
> - wrk2 按 wrk 上游设计应开 `-c` 个独立 TCP 长连接，平均分给 `-t` 个 thread 处理。本报告 HTTP 测试用 `-c50`，**预期是 ~50 条独立 socket**，但本会话没有在压测期间用 `ss -tan 'sport = :8080'` 验证过实际连接数。
>
> ### 由此得出的结论
>
> 两栏使用的客户端连接模型是不对称的：HTTP 侧每 worker 各持一条 TCP（多路并行），gRPC 侧所有 worker 共享一条 TCP（单路串行 + HTTP/2 多路复用受单连接帧处理速率约束）。所以"gRPC 600 PASS / HTTP 1000 PASS"这个对比**反映的是工具差异，不是协议或本服务的差异**。
>
> §3.2 原结论"瓶颈在 gRPC 协议层 (MaxConcurrentStreams / 连接流控)"**不成立**——当前最大嫌疑是 ghz 单 TCP 模型，而非服务端的 gRPC 配置。
>
> ### 修复
>
> - `test/perf/drivers/ghz/grpc_submit_task.sh` 已改为默认 `--connections=$CONCURRENCY`（让每个 ghz worker 各持一条连接，与 wrk2 连接模型对齐）。
> - 可通过 `GHZ_CONNECTIONS` 环境变量回退到老行为，做"单连接 multiplexing"场景的对照测试。
>
> ### 下一轮 (r4) 应做
>
> 1. 重跑前先用 `ss -tan` 实测 wrk2 与 ghz 的实际 ESTAB 连接数，把"高置信度推论"升级为"已验证"。
> 2. 在新 driver 上重跑 `grpc_submit_task` 全阶梯，覆盖本报告 §3.2 数字。
> 3. 再决定 gRPC 服务真实天花板是多少。
>
> 在那之前，**只引用本报告 HTTP 与读路径数字**，gRPC 数字仅作为"已知工具偏差下的下限参考"。

## 1. 方法论

- **工作负载模型**: open-model 固定 RPS 阶梯注入，非 closed-model VUs
- **测量窗口**: 60s/cell (wrk2 前 ~10s 为 calibration，不计入直方图)
- **阶梯**: 100 / 300 / 600 / 1000 / 2000 / 3000 / 5000 RPS
- **Verdict 规则**: `error_rate ≤ 1%` 且 `actual_rps ≥ target × 95%`
- **协议覆盖**: HTTP (wrk2) + gRPC (ghz)

> **跨协议 p99 比较注意**: wrk2 的 HdrHistogram 修正了 coordinated omission，ghz **没有**。ghz 的 p99 通常显著低于 wrk2，差异来自测量工具而非服务性能。跨协议只比较达标率与 verdict，p99 仅在同一协议内横向比较。

## 6. 已知限制与后续方向

1. **写路径天花板 ~1000 RPS**: HTTP 写入在 2000+ RPS 时 actual 骤降、延迟爆炸；gRPC 在 600+ RPS 饱和。写路径是 MySQL 持久化 + Redis LPUSH 的串行组合，瓶颈在 I/O 而非 CPU
2. **gRPC 饱和平台 ~460 RPS**（⚠️ 见顶部勘误，此结论待 r4 重测）: 2000-5000 RPS 目标下 actual 稳定在 460-510，错误率随目标升高缓慢爬升 (0.16%→0.36%)。当前最大嫌疑是 `ghz --connections=1` 单 TCP 的 HTTP/2 frame 处理速率，不是 `MaxConcurrentStreams` 或服务连接池
3. **读路径可扩展到 5000+ RPS**: MySQL 主键查询和 Redis 聚合读均可在 5000 RPS 下 PASS，CPU 多核并行 (303%) 仍有余量
4. **GOMAXPROCS=4 限制写路径**: 高 RPS 阶梯用 `LOAD_GOMAXPROCS=8`，但写路径瓶颈在 I/O 不在 CPU，提升有限
5. **loopback 拓扑**: 无网络延迟，生产环境需补充跨网络基线
