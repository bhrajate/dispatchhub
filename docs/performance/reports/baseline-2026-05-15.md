### 2. 网络场景

Toxiproxy `latency` toxic 双向（upstream/downstream）各加 RTT/2：


| 场景                  | 单向 latency / jitter | 期望 RTT  |
| ------------------- | ------------------- | ------- |
| 本机 loopback         | —                   | ~0.1 ms |
| 同区域 same-region     | 2.5 ms ±0.5 ms      | ~5 ms   |
| 跨区域 cross-region    | 15 ms ±1.5 ms       | ~30 ms  |
| 跨国 intercontinental | 100 ms ±10 ms       | ~200 ms |


### 3. 并发档与 cell 时长

每 cell 60 s constant-VUs，3 s 冷却。VU 档 = `1 / 10 / 100 / 500 / 1000`。

读路径不跑跨国（行为与写路径同构，纯 RTT-bound）。

| 接口                                | 链路                                                | 备注          |

## 六、观察与结论 (Observations)

### 1. 写入路径在 ~650 RPS 处饱和，瓶颈不在网络

四个网络场景下，HTTP 写路径在 100–500 VU 之间稳定在 **600–700 RPS**：


| 场景  | 100 VU RPS | 500 VU RPS | 增幅                      |
| --- | ---------- | ---------- | ----------------------- |
| 本机  | 641        | 655        | +2%                     |
| 同区域 | 690        | 562        | -19%（已过拐点）              |
| 跨区域 | 655        | 549        | -16%                    |
| 跨国  | 313        | 523        | +67%（200 ms RTT 让饱和点延后） |


继续往 1000 VU 加压，RPS 不增反降（吞吐 ↓ 而 p99 ↑ 一倍以上），是典型的**队列堆积** 信号——客户端排队的请求超过服务端处理能力，队头时延爆炸但每秒完成数没增加。

### 2. RTT 仅推迟"饱和点"，不改变服务端上限

低并发档（1 / 10 VU）下，RPS 完全跟随 `1/(RTT + 服务时间)`：


| 网络                       | 1 VU 实测 RPS | 1 VU 理论 RPS = 1/(RTT+服务) |
| ------------------------ | ----------- | ------------------------ |
| 本机（RTT≈0.1 ms, 服务≈10 ms） | 98.2        | ≈ 99                     |
| 同区域（RTT≈5 ms）            | 26.8        | ≈ 1/(5+30) = 28.6        |
| 跨区域（RTT≈30 ms）           | 15.4        | ≈ 1/(30+30) = 16.7       |
| 跨国（RTT≈200 ms）           | 4.1         | ≈ 1/(200+40) = 4.2       |


服务时间约 **10 ms**（loopback），高 RTT 下因 TCP 内核栈处理摊薄略上升到 30–40 ms。100 VU 之后 RTT 已被掩盖在排队时延中。

### 3. HTTP 比 gRPC 更稳，gRPC 在高并发下吞吐略低


| 协议   | 本机 100 VU RPS | 跨区域 100 VU RPS | 1000 VU 本机 RPS |
| ---- | ------------- | -------------- | -------------- |
| HTTP | 641           | 655            | 633            |
| gRPC | 604           | 458            | 401            |


gRPC 在高并发档（500 / 1000 VU）持续走低，怀疑是 k6 `k6/net/grpc` 客户端在单连接复用下的 head-of-line blocking——每个 VU 一条 HTTP/2 连接，stream 多了之后流控反压让吞吐下来。HTTP/1.1 用的是连接池，反而在这种"短而多"的请求上更平滑。

**结论**：本基线下 HTTP 比 gRPC 更适合作为吞吐入口，gRPC 的优势要在流式调用、双向通信场景下才会显现。

### 4. 读路径线性度

- **MySQL 单点读**：100 VU 后 RPS 平台在 ~1,600（受单连接池 + 单行查询限制）。跨区域 1 VU 仅 22.8 RPS（被 RTT 拉低），但 100 VU 后回到 1,055 RPS，500 VU 1,642 RPS——和本机几乎无差，说明 RTT 已被并发摊销。
- **Redis 聚合读**：四个接口里曲线最健康。500 VU 跨区域居然到了 5,631 RPS（比本机 4,649 还高），是 toxiproxy 把 burst 平滑了的副作用——连续 send 被分摊到不同的延迟桶，反而提高了 in-flight 的并发度。

### 5. 错误率

- 70 cell 中只有 1 cell（gRPC × 跨国 × 100 VU）出现 1.49% 失败。其余 0%。
- 写路径在 1000 VU 档 p99 已到 7–10 秒，业务侧用户感知会差，但 k6 默认超时 30 s 之内仍属"完成"，所以错误率为 0。

### 6. 服务端饱和的怀疑瓶颈

由于本次资源采集失败（见第五节），无法给出 CPU% / RSS 的硬证据。结合行为推断：

- **HTTP 写路径** 600–700 RPS 的天花板，单条提交平均涉及 1 次 Redis Lua（带原子 ZADD + LPUSH） + 1 次 MySQL Insert。在 10 ms 服务时间里这两项是大头，apiserver 自身 Go 编解码占小头。
- **MySQL Insert** 在共享一台主机的容器里，单连接 fsync 成本是常见瓶颈。下次开 `innodb_flush_log_at_trx_commit=2` 可作为对比基线。
- **gRPC 高 VU 下降** 大概率是 k6 客户端反压，需要换工具（ghz）或者把 k6 的 `vu : connection` 比例改 1:1 验证。

## 七、已知局限 (Known Limitations)

1. **单机 WSL2 部署**：客户端 (k6) 与服务端 (apiserver + Redis/MySQL/etcd) 在同一物理机同一内核中竞争 16 vCPU。绝对 RPS 是"服务自身吞吐上限"，端到端 延迟应理解为"任意有 RTT 的分机部署下的下界"。
2. **WSL2 loopback 虚拟化**：包经 Hyper-V vSwitch，本机环回基线 RTT 约 0.1 ms，高于裸金属 Linux loopback (~0.02 ms)。本机列不可与裸机数据直接比对。
3. **Toxiproxy 模拟有限**：只复现稳态正态抖动延迟，不覆盖真实互联网的拥塞、ECN、Head-of-Line blocking、reorder、burst loss。**跨国场景未模拟丢包**（Toxiproxy 没有 packet-loss toxic）。
4. **资源指标未采集**：`run.sh:151` 把 `/metrics` 拉取目标错配为 `:9091`，apiserver 实际暴露在 `:8080/metrics`，故 70 cell 的 server-metrics.prom 全为空文件。下次运行需先修这一行。
5. **gRPC 高并发数据偏低**：可能是 k6 `k6/net/grpc` 客户端单连接复用下的反压导致的客户端瓶颈，而不是服务端真实吞吐。需要用 `ghz` 复测确认。
6. **依赖单节点默认配置**：Redis / MySQL / etcd 均为单实例 stock 配置；无副本、分片、TLS。生产数字会因副本同步、慢盘 fsync、TLS 握手而下降。
7. **限流已禁用**：本基线为"理论上限"。生产部署受 `rate_limit.default_rate`（默认 1000/s/queue，`fc6feca` 起支持 per-queue 覆写）截顶。
8. **读路径固定 task_id**：`GET /api/v1/tasks/{id}` 全程命中同一行，MySQL InnoDB buffer pool 永远命中。冷缓存读会更慢。
9. **Payload 单一**：~256 B 固定 JSON。大 payload 会同时增加 apiserver 序列化成本与 on-wire 时间。
10. **业务约束**：所有写入命中 `queue=default, type=example.echo`，复用环境中已注册的 `worker-perf-1`。压测全程 worker 真在消费提交的任务（即 Redis  队列长度并未线性堆积），与"只压 apiserver 不压调度"的纯写入场景略有差异。
11. **k6 自身超时 30 s**：1000 VU 档 p99 已到 7–10 s，小概率请求达到 30 s 上界会被记为失败但本次 70 cell 中只观察到 1 cell 错误。单 VU 档代表 ≥ 1.5 s  平均时延也意味着实际 throughput 已远偏离健康区。
